# 决策建模链路

## 统一流程

- 新增：业务需求 → 需求分析与澄清 → 规划方案 → 人工确认方案 → 生成完整 DSL → 校验并编译 DMN → 预览与保存。
- 修改：当前草稿 DSL + 原始需求 + 调整后的业务需求（也可描述本次调整）→ 变更需求分析与澄清 → 规划并确认方案 → 生成受控变更意图 → 应用补丁生成候选 DSL → 校验并编译 DMN → 确认后保存新草稿。
- 编译继续使用确定性 DSL 编译器，不让大模型直接生成 DMN XML；未涉及的模型元素由受控补丁机制保留。
- 变更意图按元素名称定位，字段仅支持对象点路径，不接受数组下标。修改规则或参数数组时提交完整数组，保留未修改项及顺序，不能简单删除下标后写入单个成员值。
- 变更预览出现 `PATCH_TARGET` 或 `DMN_COMPILE` 时，携带诊断和上一轮意图自动重新生成，最多修复两次；模型基线冲突、权限或网络错误不自动重生成。自动修复仍受已确认方案及基线校验约束，不直接修改原草稿。
- 原始业务需求独立留存，不会被每轮修改指令覆盖，分析、规划与生成都会引用。历史需求只作背景，当前 DSL 和本次已确认方案优先，避免恢复已被修改的旧规则。导入模型没有原始需求时不虚构内容，以当前 DSL 分析。

## 关键代码

- `src/components.rs`：分析、规划、确认与生成入口；模型页的“分析需求变更”回到需求与方案页，不再直接生成变更。快捷键依照当前有效阶段推进。
- `src/workflow_api.rs`：读取当前 DSL 与原始需求，供分析和规划使用；保存分析时清除旧方案与确认标记。
- `src/workflow.rs`：需求与模型基线匹配、已确认方案到生成指令的统一转换。
- `src/api.rs`：DSL 生成、流水线和变更意图接口从服务端读取已确认方案构造指令，不能靠请求文本绕过分析与确认。
- `src/nl_dsl/agent.rs`：分析、规划与变更生成各自负责独立阶段；修改规划明确调整范围、保留规则及回归验收条件。

## 失效与并发保护

- 工作流保存 `baseRevision`，它是分析时的草稿版本数据库 ID，不是展示用的版本号。新建模型时为 `null`。
- 需求文本变化后，前端标记“待重新分析”，旧结果保留供参考，但不可用于生成。
- 规划后的澄清回答变化时，必须重新规划，不能确认旧方案。
- 规划和确认接口必须携带 `expectedUpdatedAt`；生成接口必须携带 `workflowUpdatedAt`，值来自已加载工作流的 `updatedAt`。
- 分析、规划保存采用工作流时间戳比较，避免较早的请求覆盖较新的分析或方案；同时核对当前草稿基线。
- 生成前后均核对工作流快照；生成期间需求、方案或草稿变化时废弃结果。普通接口返回冲突，已建立的 SSE 连接发送 `error` 事件而不是成功结果。
- 模型基线发生变化后旧方案不能继续生成，必须基于新草稿重新分析。保存后的下一轮修改也必须重新走分析与规划。
- 生成失败保留业务需求和已确认方案，可在基线未变化的情况下重试；预览待确认时锁定新分析与生成，需先保存或放弃候选。

## 数据库升级

已有数据库在部署新服务前执行：

```sh
psql -U <管理员> -d fuxi_dmn -f script/021_workflow_model_baseline.sql
```

迁移新增可空的 `decision_workflows.base_revision` 与 `original_requirement_text`，不修改已有草稿或业务需求。已有模型的旧工作流没有绑定基线，因此首次修改需要重新分析；无草稿的新建工作流可继续使用。全新数据库的初始化脚本已包含这些字段。

## 验证场景

1. 新项目完成分析、必答问题、方案确认后才可生成 DSL/DMN。
2. 已有模型编辑需求，先看到分析结果和方案，再生成变更预览；未确认前原草稿不变。
3. 修改需求后按钮和快捷键都不能使用旧方案；编辑澄清回答后不能确认旧规划。
4. 规划或生成期间其他用户更新工作流或模型基线，旧请求返回冲突（已建立的 SSE 连接发送错误事件），不覆盖新结果。
5. 缺少方案确认、工作流时间戳或基线不匹配的生成请求被服务端拒绝。
6. 候选保存后再次修改，需要以新草稿重新分析；生成失败则可保留方案重试。
